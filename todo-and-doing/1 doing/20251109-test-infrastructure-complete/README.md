## 🚨 核心问题回顾

### 为什么需要这个需求？

**痛点**：bookmark → outline 重构后，bug层出不穷，陷入"修A坏B"恶性循环

**数据**：
- 反复调试时间：半个多月，每天3小时
- 单次重构成本：10人天（当前） vs 3人天（目标）
- 问题发现延迟：2-3天（手动测试） vs 5分钟（目标：CI）

### 四大根因

1. **契约散落**：事件名、消息类型前后端"手改两遍"
2. **测试金字塔倒置**：缺契约测试，单元测试质量参差
3. **状态机隐式化**：复杂流程分支散落，易遗漏
4. **回归测试不充分**：测试通过但功能错误

### 核心解决方案

1. **后端测试优先**：不依赖浏览器，最稳定
2. **契约测试**：保证前后端接口对齐
3. **金标准对比**：人工验证的正确结果
4. **故意改错法**：验证测试真正有效

## 💡 关键原则

### 测试质量 > 测试数量

**识别假测试的标志**：
- ❌ 只验证"调用了某个函数"
- ❌ Mock了90%的依赖
- ❌ 只测Happy Path
- ❌ 把代码改错了，测试还通过

**好测试的标志**：
- ✅ 测试真实行为，而非实现细节
- ✅ 用真实数据（或接近真实）
- ✅ 覆盖边界情况
- ✅ 破坏代码后必然失败

### 测试环境问题

**核心认知**：Playwright (Chromium) ≠ QtWebEngine

**解决方案**：
1. 优先写后端测试（不依赖浏览器）
2. 契约测试保证前后端对齐
3. 最后在QtWebEngine手动验证

## 🔧 开发者指南

### 如何判断是否该写测试？

**立即写测试**：
- 修复bug后（防回归）
- 添加新功能后
- 重构代码前（保护网）

**可以延后**：
- 一次性脚本
- UI微调（颜色、间距）
- 临时调试代码

### 如何判断测试质量？

**故意改错法**：
1. 运行测试，确保通过
2. 故意破坏被测代码
3. 再次运行测试
4. 如果测试失败 ✅ → 有效
5. 如果测试仍通过 ❌ → 假测试，重写

### 如何写集成测试？

**原则**：
- 少Mock，多真实
- 测试完整流程，而非单个函数
- 用真实数据库、真实API
- 验证用户可见的结果
