## 📋 需求概述

### 背景

**核心问题**：bookmark → outline 重构引发大量回归bug，修复陷入"修A坏B"的恶性循环

**痛点统计**（最近1个月）：
- 反复调试时间：半个多月，每天3小时
- 典型问题：
  - 首次导入不落库（后端API字段不一致）
  - 修改失败，刷新回退（前端未消费WebSocket回执）
  - ESLint修复引入功能bug（误删关键逻辑）
  - 事件名称错误（常量不存在，运行时才发现）
  - 多次渲染（3次jsTree ready）

**根因分析**（4大核心问题）：
1. **契约散落**：事件名、消息类型、API字段前后端"手改两遍"，易不同步
2. **测试金字塔倒置**：缺契约测试（最高ROI），单元测试质量参差
3. **状态机隐式化**：复杂流程分支散落各处，易遗漏场景
4. **回归测试不充分**：修改后无自动验证，手动测试延迟2-3天才发现

**测试环境差异问题**：
- Playwright (Chromium) 测试通过 ≠ QtWebEngine 实际运行正常
- E2E测试不可靠，需要更底层的测试策略

## 🎯 需求目标

### 核心目标

1. **建立可靠的测试体系**：
   - 测试通过 = 功能真的正确（不是假通过）
   - 测试失败 = 立即知道哪个功能坏了

2. **防止回归**：
   - 修改A不会破坏B
   - 重构有信心（测试保护）

3. **快速反馈**：
   - 问题发现延迟从天级降到秒级
   - 修复成本降低90%

### 量化指标

| 指标 | 当前值 | 目标值 | 验收标准 |
|------|--------|--------|----------|
| 回归bug率 | 1次修改引入0.3个新bug | <0.05 | 连续2周无回归 |
| 问题发现延迟 | 2-3天（手动测试） | <5分钟（CI自动发现） | CI通过=功能正确 |
| 测试覆盖率 | 约50%，质量参差 | 核心模块>80% | 关键路径100%覆盖 |
| 单次重构成本 | 10人天 | 3人天 | 实际重构验证 |
| 测试可靠性 | 测试通过但功能错误 | 测试通过=功能正确 | 故意改错法验证 |

## 📐 技术方案

### 测试金字塔（新架构）

```
                  /\
                 /  \  QtWebEngine手动测试 (2-3个关键路径)
                /____\  运行时间: 人工，频率: 发布前
               /      \
              /________\  契约测试 (15-20个)
             /          \  运行时间: <30s，频率: 每次提交
            /____________\
           /              \  后端API集成测试 (20-30个)
          /________________\  运行时间: <1min，频率: 每次提交
         /                  \
        /____________________\  后端单元测试 (50+)
       /                      \  运行时间: <10s，频率: 每次提交
```

**关键原则**：
1. ✅ 后端测试优先（不依赖浏览器，最稳定）
2. ✅ 契约测试是关键（保证前后端接口对齐）
3. ✅ 避免Playwright E2E（与QtWebEngine环境不一致）
4. ✅ 金标准对比（人工验证的正确结果）

### 测试分层详解

| 测试层级 | 数量目标 | 运行时间 | 测试什么 | 失败时说明 |
|---------|----------|----------|----------|-----------|
| 后端单元测试 | 50+ | <10s | 单个函数逻辑 | 代码逻辑错误 |
| 后端API集成 | 20-30 | <1min | 完整CRUD流程 | 业务流程错误 |
| 契约测试 | 15-20 | <30s | 前后端消息格式 | 接口不兼容 |
| QtWebEngine手动 | 2-3 | 人工 | 关键用户路径 | UI/交互问题 |

## 📌 附录

### 核心认知

1. **测试不是成本，是投资**：1元测试投资 = 避免10元bug修复成本
2. **快速反馈是王道**：秒级发现 vs 天级发现 = 1000倍成本差距
3. **契约即代码**：Schema生成前后端常量，别再手写两遍
4. **测试质量 > 测试数量**：测试通过但功能错误，比没测试更危险

### 禁止事项

❌ 在测试覆盖不足时大规模重构（只会引入更多bug）
❌ 忽略失败的测试（失败的测试就像火警）
❌ 依赖手动测试（不可重复、不可规模化）
❌ 写Mock过度的测试（Mock了所有逻辑=测了个寂寞）
❌ 只测Happy Path（边界情况才是bug高发区）
