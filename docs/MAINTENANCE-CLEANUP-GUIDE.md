# MAINTENANCE-CLEANUP-GUIDE

> 维护两类内容：① 过时代码的清理；② 过时文档的清理。目标是在**不丢失历史信息**的前提下，让代码库和文档保持精简、可读、可维护。

---

## 1. 范围与角色

- 适用范围：
  - 后端：`src/backend/**`
  - 前端：`src/frontend/**`
  - 文档：`docs/**`、`.kilocode/rules/memory-bank/**`、`todo-and-doing/**`
- 适用场景：
  - 功能被新实现完全取代，需要清理旧代码 / 旧接口；
  - 某篇文档描述的设计/流程已过时，需要更新或归档；
  - Memory Bank / AItemp 中历史信息过多，需要压缩、迁移到 ARCHIVE。

---

## 2. 过时代码清理流程

### 2.1 识别“过时代码”

优先通过 **事实依据** 判断是否过时，而不是感觉：

- 功能级别：
  - 已有新模块替换旧实现（例如 `v2`/`v3` 版本已在 docs/ 或 tech.md 写明），旧模块仅保留兼容路径；
  - Feature flag 永久关闭，且近期没有重新启用计划；
  - API/消息类型在 contracts 或 standards 中标记为 deprecated。
- 技术信号：
  - 单元测试/集成测试中已不再引用的模块；
  - ESLint/静态检查长期提示“未使用”的导出/函数；
  - docs/ 中已有“历史设计”章节说明该实现仅供参考，不再使用。

若缺乏明确证据（例如没有文档说明、没有 flag 标记），**先补充文档/Memory Bank 记录，再进行清理决策**。

### 2.2 清理前准备

在动手删除/重构代码前，建议按以下顺序准备：

1. 在 `todo-and-doing/` 中为“清理任务”建一条记录（可复用已有任务），明确：范围、风险点、回滚策略。
2. 检查相关文档：
   - `docs/architecture/*`、`docs/TECH/*`、`docs/contracts/*` 中是否提到该模块/接口；
   - `.kilocode/rules/memory-bank/context.md` 是否有仍在使用的说明。
3. 为要清理的行为补上防回归测试：
   - 如果是“旧实现已经不再被调用”，测试应验证**新路径**正常工作，而不是仅测试“旧文件存在”；
   - 若清理的是兼容分支（例如 old/classic 版本），确保新版本已有覆盖测试。

### 2.3 实施步骤（代码层面）

推荐小步执行，避免一次性大规模删除：

1. **先移除入口引用**：
   - 从容器、路由、Feature registry、WS 消息分发等入口处移除对旧模块的注册和调用；
   - 确认运行路径已经不可能走到旧实现。
2. **再删除内部实现文件**：
   - 删除不再被引用的旧实现文件/类/函数；
   - 同步清理对应的测试文件（若不再有意义）或改为测试新实现。
3. **清理常量与配置**：
   - 删除已弃用的 feature flag、环境变量、事件常量、消息类型常量等；
   - 在 contracts / standards 中同步更新枚举/表格。
4. **运行静态检查与测试**：
   - 至少运行与改动范围相关的 eslint / pytest / jest；
   - 确认没有因删除旧代码引起的新警告或错误。

### 2.4 记录与可追溯性

清理过时代码后，必须保证“**从哪儿看得到这次清理**”：

- 在 `.kilocode/rules/memory-bank/context.md` 中：
  - 追加一条“某模块旧实现已移除，仅保留新实现”的记录；
  - 标明旧文件路径、新文件路径、清理由来（性能/维护/安全等）。
- 如有必要，在 `docs/history` 或 `docs/ARCHIVE` 下记录较大规模的重构/清理背景。

## 3. 过时文档清理流程

### 3.1 识别“过时文档”

常见信号：

- 文档描述的模块/文件已经不存在，或路径已更名；
- 流程说明与当前代码实现明显不一致（例如旧的导航策略、旧的 WS 协议）；
- 同一主题存在多份文档且内容冲突，其中旧文档未被引用；
- Memory Bank context 中已将某些设计标记为“历史版本/仅供参考”。

### 3.2 清理原则

1. **默认不直接删除文档**：
   - 优先移动到 `docs/ARCHIVE` 或在文档顶部标记为 Deprecated；
   - 只有在内容完全无价值（如重复模板、临时草稿）且已确认不会再用时，才考虑删除。
2. **保持入口索引一致**：
   - 若在 `docs/index`、`docs/TECH`、`docs/standards` 等目录有指向该文档的链接，需要同步更新；
   - 确保“新人从 index 看到的内容”永远是最新的。
3. **配合 Memory Bank 压缩机制**：
   - 对于 `.kilocode/rules/memory-bank/context.md` 中过旧且已归档到 `docs/context-archive` 的内容，遵守压缩规则，只做迁移与归档，不直接删行。

### 3.3 实施步骤（文档层面）

1. 确认替代文档：
   - 如果已经有新的架构/测试/规范文档替代旧文档，在新文档顶部注明“替代了哪份旧文档”；
   - 在旧文档顶部说明“本内容已过时，请参考 XXX”。
2. 归档或更新：
   - 归档：将旧文档移动到 `docs/ARCHIVE` 或对应历史目录，并在文件顶部添加“Deprecated / Archived”标记；
   - 更新：如果旧文档仍有部分内容有效，可以直接在原文件上更新，使其与现状一致。
3. 更新索引与引用：
   - 搜索仓库中对该文档的引用（例如在 README、index 文档中的链接），统一指向新的文档或 ARCHIVE 位置；
   - 确保 CI/自动化脚本（如果有）中不再依赖旧路径。

### 3.4 记录与追踪

- 在 `.kilocode/rules/memory-bank/context.md` 中：
  - 简要记录“哪份文档被归档/更新，为何过时，现在应看哪份文档”；
  - 有助于理解历史决策、避免反复讨论同一问题。
- 如涉及较大范围的文档重组（例如测试体系、架构文档整体改版），建议在 `docs/history` 中写一份变更说明。

## 4. 开发者自检清单（TL;DR）

在准备“清理过时代码或过时文档”前，可快速过一遍：

1. 我能否说明“为什么它是过时的”？有没有文档/flag/替代实现作为事实依据？
2. 清理前是否确保新实现稳定，有测试覆盖？
3. 清理时是否先断开入口，再删除内部实现/文档？
4. 是否在 Memory Bank context / docs/history 中留下了痕迹，方便以后追溯？
5. 是否检查并更新了相关索引（docs/index、TECH、standards 等）？

如果上述问题有任意一条回答“不确定”，建议先补充事实和文档，再进行清理操作。
